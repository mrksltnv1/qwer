# Алгоритм мониторинга и переключения

## Проверка доступности

`TcpProbe` делает TCP-handshake на порт 443. Не ICMP: raw ICMP требует root,
часто фильтруется, и один недоступный адрес не доказывает отказ туннеля.

**Дедлайн (найден и исправлен дважды на живом тесте):**

1. `Socket.connect(addr, timeout)` ограничивает *connect*, но **не** DNS-резолв,
   который выполняется при построении адреса из hostname. При реальном отказе
   резолв блокировался ~25 с и растягивал цикл с 2.5 с до 27 с.
2. Дедлайна на цель недостаточно: при N целях худший случай N × дедлайн, что
   ломает ритм выборки, на который опирается окно отказа.

Итог: `probe()` возвращается за `totalDeadlineMillis` (2 с) в худшем случае.
Все цели опрашиваются параллельно в общем бюджете; IP-литералы идут первыми
(DNS не нужен), hostnames — как второе мнение.

**Защита от утечки:** проба не создаёт свой маршрут и не привязывается к
физическому интерфейсу. Она идёт из процесса приложения через активный
VpnService, то есть по туннелю, как любой другой трафик. Проверка «в обход»
была бы ровно той утечкой, от которой мы защищаемся.

## Условия переключения

```kotlin
FailoverConfig(
    probeIntervalMillis   = 2_500,   // опрос
    failureWindowMillis   = 12_000,  // окно устойчивого отказа
    minConsecutiveFailures = 3,      // минимум неудач в окне
    cooldownMillis        = 60_000,  // пауза после переключения
    maxAutoSwitches       = 3,       // бюджет на сессию
    stabilityResetMillis  = 600_000, // 10 мин стабильности → бюджет восстанавливается
    trafficStagnationMillis = 90_000 // застой RX/TX — только подсказка
)
```

## Правила автомата

| № | Правило | Тест |
| --- | --- | --- |
| 1 | Успешная проба сбрасывает накопленный отказ | `recovery inside the window cancels the switch` |
| 2 | Нужны И полное окно, И минимум неудач | `window alone is not enough without the minimum failure count` |
| 3 | Нет физической сети → не виним туннель | `no physical network never blames the tunnel` |
| 4 | Замершие счётчики сами по себе не переключают | `frozen counters alone never trigger a switch` |
| 5 | Cooldown подавляет повторное переключение | `cooldown suppresses a second switch right after the first` |
| 6 | Бюджет ограничивает WG→WDTT→WG→WDTT | `switch budget stops endless oscillation` |
| 7 | Долгая стабильность восполняет бюджет | `long stability refills the switch budget` |
| 8 | Нет резервного профиля → GiveUp, не Switch | `missing failover target gives up instead of switching` |

**Модель времени в тестах:** окно отсчитывается от *первой наблюдённой* неудачи,
не от момента реальной поломки. При интервале 2.5 с и окне 12 с первое возможное
переключение — на 15-й секунде (шестая неудача). Ошибка в эту сторону безопасна:
лучше переключиться позже, чем дёргаться на кратковременном сбое.

```
              why=нет связи 13 c, неудачных проверок: 4
```

Отказ обнаружен → переключение за **13 секунд**. Интервал проб после исправления
держался ровно 2.46–2.56 с (проверено по меткам 10:13:23 … 10:13:41).

## Чего НЕ делаем

- **Не возвращаемся автоматически** на WireGuard после переключения. Безопасная
  политика failback не реализована и не протестирована, поэтому её нет.
- **Не выдаём handover за бесшовное переключение.** WDTT Plus — другое приложение;
  UI честно пишет, что подключиться нужно в нём.
- **Не считаем замершие счётчики доказательством.** Пользователь может просто ничего
  не делать, и RX/TX законно не меняются.
